# R1.7 — Critical rendering path (follow-up to R1.6)

## Goal

Bring Lighthouse mobile on `/home`, `/ms` and `/zh` to Performance >= 95 and LCP <= 2.0 s (simulated throttling, 360x640, Moto G4 class) without changing copy, hierarchy, facts or desktop layout. R1.6 measured Performance 84-85 and LCP 3.7-3.9 s on every route, including `/fees` and `/apply` which have no hero image, and showed the text LCP element waits ~2.4 s to paint after a 22 ms TTFB. The cause is shared critical-path weight competing for bandwidth before first paint: 4 preloaded font files (108 KB), ~37 KB gzipped render-blocking CSS from a 161 KB source stylesheet, ~190-220 KB gzipped JS, and ~70 KB HTML. R1.6 was not allowed to touch fonts, JS or CSS beyond additions; this brief is.

## Model and role

Sonnet, single technical executor. No reviewer pass.

## Constraints

- No copy, fact, heading-hierarchy, colour or desktop-layout changes. Mobile layout order may not change (R1.6 proved reordering the hero makes LCP worse).
- Facts never change; banned patterns still apply; you add no prose.
- Branch `feat/r1-7-critical-path` from `codex/hostinger-deployment`. Push the feature branch only. Never merge into or push `codex/hostinger-deployment` or `main`.
- Measure with Lighthouse 13 CLI, mobile preset, simulated throttling, three runs per route, report the median. Same method before and after every lever so numbers are comparable.
- Do not raise or remove a threshold. If a lever does not help, revert it and record the numbers.

## Levers, in order (measure after each; stop when both targets are met on all three routes)

1. **Fonts.** In all three layouts: `preload: false` on `IBM_Plex_Mono` and `Archivo` (keep `display: "optional"`), keep the display serif preloaded because the hero `h1` uses it; if the serif is still the largest preload, restrict it to the weights actually used (check `globals.css` for `font-weight` on `h1-h3`). Confirm no e2e font assertion breaks. Expected gain: ~70 KB off the pre-paint queue.
2. **JS deferral.** Load below-the-fold or interaction-only client components with `next/dynamic` and `ssr: false` where they render nothing meaningful on the server: `ProgrammeAssistant` (mount on first interaction or after `requestIdleCallback`), `ExecutiveDiagnostic` on `/home` if present, `YouTubeFilm` facade script. Keep `LeadForm` server-rendered (it is a conversion surface and part of the hero on mobile); only defer its Turnstile script, which is already lazy. `ConsentBanner` and `GoogleTagManager` may mount after idle. Verify `npm run test:e2e` still passes, especially the Turnstile-deferral tests at lines ~626-667.
3. **CSS weight.** Run Chrome coverage on the five routes (`/home`, `/ms`, `/zh`, `/fees`, `/apply`) at 360 and 1440 widths and remove rule blocks in `globals.css` that are unused on every route in the built site, one section at a time (candidates from the class names: `home-slide`, `working-hero`, `cold-funnel-*`, `campaign-path` if no campaign route uses them, legacy hero rules). After each removal run `npm run build`, `audit:styles`, `test:e2e`. Target gzipped CSS <= 25 KB. Never delete a rule used by any built route or by `legacy/` (legacy is not built).
4. **HTML weight.** Check `/home` HTML for duplicated JSON-LD graphs or oversized inline data; if the site-wide `@graph` and page schema repeat large blocks, dedupe by `@id` references. Target HTML <= 50 KB gzipped-equivalent transfer.
5. **Hero image response.** Confirm the image is served as AVIF/WebP at `w=1080` or lower on mobile via `sizes`; add `decoding="async"` only if Lighthouse flags it.
