# R1.6 — Performance and fonts

## Goal

Add explicit CJK fallback stacks so `/zh` renders in a chosen Chinese face rather than whatever the device picks, then measure the whole site against the spec's performance bar and fix anything that misses it. This brief is measurement-led: the deliverable is a recorded set of numbers plus the minimum fixes needed to hit the thresholds.

## Model and role

Sonnet, single technical executor. No reviewer pass.

## Inputs — read these first, in full

- `docs/superpowers/specs/2026-09-03-site-quality-programme-design.md` (sections 1 item 5, and R1.6)
- `src/app/globals.css` — the `:root` and `body` type declarations, and the `--font-fraunces` / `--font-archivo` / `--font-plex-mono` variables
- The three locale layouts that declare `next/font` (`grep -rn "next/font" src/app`)
- `src/app/(zh)/zh/layout.tsx` — confirm the `lang` attribute it emits
- `next.config.ts`
- `scripts/style-budget-audit.mjs` (the inline-style, `<style` and `!important` ceilings)
- `docs/superpowers/research/site-map.md` section 6 (fonts, CSS size, third-party scripts)

## Constraints

- **Facts never change.** No copy edits at all.
- **Keep the three `next/font` families.** Do not add a fourth webfont, do not self-host a CJK webfont, do not add `@font-face`. Chinese and Malay continue to rely on system faces; this brief only names which system faces, in which order.
- **No `globals.css` refactor.** The only structural edits permitted are: adding the CJK fallback declarations, and removing dead video rules **if and only if R1.1 has not already removed them** (check first; if `grep -n "commerce-media-control" src/app/globals.css` is empty, R1.1 is merged and you touch nothing there).
- **Branch and release action.** Create `feat/r1-6-performance-fonts` from `codex/hostinger-deployment`. Pushing your feature branch to GitHub for CI is allowed. Merging into `codex/hostinger-deployment` and pushing that branch **is the deployment**; it happens only after the full section-6 gate is green. Never do that from this brief.
- Hostinger configuration is out of scope for the whole programme. All measurements are against a local production build (`npm run build && npm start`), never against the live site.
- Run this brief **after** R1.1 merges. Hero LCP is R1.1's deliverable; measuring before it merges produces numbers that describe the old video.
- Do not raise a threshold to make a measurement pass. If a target is unreachable, report the number and the reason.

## Steps

1. `git checkout codex/hostinger-deployment && git pull --ff-only 2>/dev/null; git checkout -b feat/r1-6-performance-fonts`. Confirm the hero image change from R1.1 is present (`grep -n "hero-leader.webp" src/components/site/CommerceHeroMedia.tsx`); if it is not, stop and report that R1.1 has not merged.
2. **CJK fallbacks.** Confirm the Chinese layout emits `lang="zh-Hans-MY"` (the map records this; verify it). In `src/app/globals.css`, add near the existing body/heading type rules:
   ```css
   :lang(zh-Hans-MY) body,
   [lang="zh-Hans-MY"] body,
   [lang="zh-Hans-MY"] p,
   [lang="zh-Hans-MY"] li,
   [lang="zh-Hans-MY"] td,
   [lang="zh-Hans-MY"] th{font-family:var(--font-archivo),"PingFang SC","Hiragino Sans GB","Microsoft YaHei","Noto Sans CJK SC","Noto Sans SC",sans-serif}
   [lang="zh-Hans-MY"] h1,[lang="zh-Hans-MY"] h2,[lang="zh-Hans-MY"] h3,[lang="zh-Hans-MY"] h4{font-family:var(--font-fraunces),"PingFang SC","Hiragino Sans GB","Microsoft YaHei","Noto Sans CJK SC","Noto Sans SC",sans-serif}
   ```
   Keep the Latin variable first in each stack so English words inside Chinese sentences stay in the site face. Match the file's existing single-line, no-space declaration style.
3. Run `npm run audit:styles` and confirm the inline-style, `<style` and `!important` counts are unchanged. Adding a stylesheet rule must not move any of the three budgets.
4. **Build and serve for measurement.** `npm run build && npm start`. All measurements below are against this production build, not `next dev`.
5. **Lighthouse, mobile, Moto G4 profile.** Run Lighthouse mobile on `/home`, `/ms` and `/zh`. Record for each: Performance, Accessibility, Best Practices, SEO, LCP (seconds), CLS, INP (or TBT where INP is unavailable in a lab run), and the named LCP element. Required: **Performance >= 95, Accessibility 100, Best Practices 100, SEO 100, LCP <= 2.0 s, CLS 0** on all three.
6. **Extend the measurement set.** Run the same mobile profile on `/fees` and `/apply` and record LCP, CLS and INP/TBT. The spec requires the numbers to be recorded for these two routes; the pass/fail bar in section 1 item 5 applies to `/home`, `/ms` and `/zh`.
7. **Record the asset budget.** For each of the five routes record: gzipped CSS transferred, JS transferred, and total transfer excluding fonts. Get gzipped CSS from the DevTools Network panel `Size` column for the `/_next/static/css/*.css` request with `Use large request rows` on, or `curl -s -H "Accept-Encoding: gzip" <css-url> | wc -c`.
8. **Fix only what misses.** Work the failures in this order, and only as far as needed to clear the bar:
   - LCP: confirm the hero image carries `priority` + `fetchPriority="high"` and that Next.js is serving AVIF/WebP (check the `content-type` of the `/_next/image` response). If `images.formats` is absent, R1.1 owns adding it — verify it landed.
   - CLS: find the shifting element with the Performance panel's Layout Shift records. Fix by reserving space (explicit `width`/`height` or `aspect-ratio`) in `globals.css`. Never fix a shift by disabling an animation.
   - Accessibility below 100: fix the specific axe rule Lighthouse names, in the component that owns it.
   - Best Practices below 100: usually a console error or a missing `charset`; fix the named cause.
   - JS or CSS over budget with everything else green: report the number, do not refactor.
9. Re-measure every route after each fix. Do not batch fixes and measure once.
10. Run the full gate (see Acceptance). Commit as `feat(css): add explicit CJK fallback stacks for zh-Hans-MY` plus one commit per performance fix, each naming the metric it moved.
