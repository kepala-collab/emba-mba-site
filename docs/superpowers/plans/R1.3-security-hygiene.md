# R1.3 — Security hygiene (application side only)

## Goal

Lock the Content-Security-Policy behaviour the application already has behind a unit test, so no future change can silently drop a directive or leak `frame-ancestors` into the meta variant. Refresh `public/.well-known/security.txt` with Malay and a one-year expiry extension. Host and CDN configuration is explicitly out of scope.

## Model and role

Sonnet, single technical executor. No reviewer pass.

## Inputs — read these first, in full

- `docs/superpowers/specs/2026-09-03-site-quality-programme-design.md` (section R1.3, and section 1 item 4)
- `src/lib/content-security-policy.ts` (31 lines — it exports `contentSecurityPolicyHeader` and `contentSecurityPolicyMeta`, both built from one `directives` array)
- `scripts/verify-public-release.mjs` — note line 54, which prints either `response-header CSP` or `HTML CSP fallback + X-Frame-Options DENY`; either is a pass
- `next.config.ts` headers function, and `src/proxy.ts` if present, for where the header is applied
- `public/.well-known/security.txt` (4 lines)
- `vitest.config.mts` — tests must match `src/**/*.test.ts`

## Constraints

- **Facts never change.** No copy edits anywhere.
- **Do not change the policy.** `src/lib/content-security-policy.ts` is correct as written. You are adding a test that describes it, not rewriting it. If a directive is missing that the spec requires, report it rather than adding it silently.
- **Host CDN configuration is out of scope.** Do not write a Hostinger runbook, do not attempt to log into any host or CDN panel, do not request credentials, and do not run anything against the live site. `verify-public-release.mjs` passing in **fallback mode** is an acceptable outcome for this programme.
- **Branch and release action.** Create `feat/r1-3-security-hygiene` from `codex/hostinger-deployment`. Pushing your feature branch to GitHub for CI is allowed. Merging into `codex/hostinger-deployment` and pushing that branch **is the deployment**; it happens only after the full section-6 gate is green. Never do that from this brief.
- `frame-ancestors` is deliberately header-only. The meta variant omitting it is correct behaviour, not a bug — the comment at `content-security-policy.ts:25-26` explains why.

## Steps

1. `git checkout codex/hostinger-deployment && git checkout -b feat/r1-3-security-hygiene`.
2. **Write the failing test first.** Create `src/lib/__tests__/content-security-policy.test.ts`. Import both exports. Assert:
   - `contentSecurityPolicyHeader` contains each of `default-src 'self'`, `object-src 'none'`, `form-action 'self'`, `frame-ancestors 'none'`, `base-uri 'self'`, `manifest-src 'self'`, `worker-src 'self' blob:` and `media-src 'self'`.
   - `contentSecurityPolicyMeta` contains every directive above **except** `frame-ancestors`, and `expect(contentSecurityPolicyMeta).not.toContain("frame-ancestors")`.
   - The two strings differ by exactly the `frame-ancestors 'none'` segment: split both on `"; "`, and assert `headerParts.filter(p => !p.startsWith("frame-ancestors"))` deep-equals `metaParts`. This is the assertion that actually protects the invariant; the individual `toContain` checks are documentation.
   - `script-src` includes `https://challenges.cloudflare.com` and `'unsafe-inline'`.
   - `frame-src` includes both `https://challenges.cloudflare.com` and `https://www.youtube-nocookie.com`.
   - Neither string contains `'unsafe-eval'` when `process.env.NODE_ENV !== "development"`. Vitest runs with `NODE_ENV=test`, so this holds; assert it rather than assuming.
3. Run `npm test`. If every assertion passes on the first run, the test is describing existing behaviour correctly — that is the expected outcome here, since this brief locks behaviour rather than changing it. If any assertion **fails**, stop: you have found a real gap between the spec and the code. Record the exact failure in the hand-back and do not "fix" the policy to make the test green without saying so.
4. **security.txt.** Edit `public/.well-known/security.txt`:
   - `Preferred-Languages: en, ms, zh`
   - `Expires:` extend by exactly one year, from `2027-08-11T00:00:00.000Z` to `2028-08-11T00:00:00.000Z`.
   - Leave `Contact:` and `Canonical:` untouched.
5. **Confirm the header is still applied in both places.** Grep for both exports: `grep -rn "contentSecurityPolicyHeader\|contentSecurityPolicyMeta" src/ next.config.ts`. Confirm the header export feeds `next.config.ts` headers (and the middleware/proxy if one exists) and the meta export feeds a `<meta http-equiv>` in each locale layout. Do not change any of these wirings; just record what you found in the hand-back.
6. **Verify locally.** `npm run build && npm start`, then in another shell:
   - `curl -sI http://localhost:3000/ms | grep -i content-security-policy` — must show a full policy containing `default-src 'self'` and `frame-ancestors 'none'`.
   - `curl -s http://localhost:3000/ms | grep -o 'http-equiv="Content-Security-Policy"[^>]*'` — must show the meta variant, and it must not contain `frame-ancestors`.
   Record both outputs.
7. Run the full gate (see Acceptance). Then `npm run release:sync && npm run release:check`, since `public/` changed.
8. Commit as two commits: `test(csp): lock the header and meta policy invariants`, then `chore(security-txt): add Malay and extend the expiry by one year`.

Not part of acceptance, and not to be run: anything against `https://futurereadymba.com`, and `node scripts/verify-public-release.mjs`. Those are release-time checks the architect runs after deployment.

## Out of scope

Any change to `src/lib/content-security-policy.ts`. Any Hostinger or CDN work, runbook or ticket. Adding a CSP `report-uri`. Removing `'unsafe-inline'` from `script-src` or `style-src` (that is a design-system change, excluded by spec section 2). Any other `.well-known` file. Rate limits, Turnstile, or any other security surface.
